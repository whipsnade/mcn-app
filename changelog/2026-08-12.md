## 独立审核收口：in-process server 启动失败的 task 泄漏

### 背景与目标

方案 B 最终独立审核在 `e362e47` 上提出最后一项 Important：
`backend/tests/integration/pi_uat/harness.py` 的 `_InProcessServer.start()` 在创建
serve task 后，若 5 秒轮询窗口内 `started` 仍为 False，直接抛
`in_process_server_start_timeout`，但不 cancel/gather serve task；同时
`PiUatTopology._start_topology()` 只有 `await server.start()` 成功后才把 server 追加到
`self._servers`，启动失败时外层 cleanup 看不到该 server，serve task/监听/端口可能跨拓扑残留。

最小复现：`in_process_server_start_timeout task_done=False active=False`。

### 红灯复现（先写测试，确认失败）

`tests/integration/pi_uat/test_harness_lifecycle.py` 新增两个测试，轮询 sleep 经
monkeypatch 缩到 0，不真实等待 5 秒：

- `test_in_process_start_timeout_cancels_and_reaps_serve_task`：fake uvicorn
  （started 恒 False、serve 长期等待）启动超时后，断言 serve task 已 done/cancelled、
  实例不在 `_active_servers`、无遗留 watcher/task。
- `test_topology_reaps_in_process_server_when_start_fails`：拓扑级反例——fake server
  启动失败后外层 `__aenter__` cleanup 仍完成、已创建 task 完整收口、端口可重新 bind
  （无监听残留）、DB teardown 仍执行、抛出的仍是原始
  `in_process_server_start_timeout`（不被 cleanup 吞掉）。

红灯实证：两个测试均失败于 `task_done=False`（serve task pending 泄漏），0.07s 内完成。

### 修复方法（仅测试基础设施，不动生产业务逻辑）

- `_InProcessServer.start()`：轮询窗口整体包 try/except BaseException——超时、
  serve 提前退出（新增检测，报 `in_process_server_start_aborted` 并链上 serve 异常）、
  取消，统一经新增的 `_abort_failed_start()` 有界收口后原样 re-raise。
  `_abort_failed_start()` 设置 `should_exit`（AppStatus 与 server）、cancel serve task、
  复用现有 `_reap_tasks_bounded`（timeout=2，报 `in_process_server_abort_timeout`）、
  经 `_drain_sse_shutdown_watchers` 只收本 server 创建的 watcher，finally 中维护
  `_active_servers`/AppStatus 一致性（仅空集时重置全局标志）。收口自身失败会继续抛错，
  绝不把失败启动静默伪装成成功；不使用无限 gather，不新增固定 sleep，不扩大 timeout。
- `_start_topology()` 改为先 `self._servers.append(server)` 再 `await server.start()`：
  start 已具备失败自清理语义，登记保证外层 cleanup 的 `server.stop()` 作为第二道防线。
