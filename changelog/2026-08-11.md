# 2026-08-11

## 方案 B 第二轮阻断修复

### 背景与目标

修复方案 B 第二轮审核发现的生产 Pi Gateway MCP readiness 与离线 UAT 生命周期问题。
本日不调用真实模型、DataTap、钱包/积分，不触碰历史真实 Task 9、真实 B7 UAT、生产切流或方案 C。
`changelog/2026-08-10.md` 中已有的 8 月 11 日复审事实保持原样；本文件补充本日新修复证据，不覆盖旧记录。

### 主要改动

- R1 建立有界 `McpReadinessGate`：生产 adapter 使用 eager lifecycle，等待公开状态事件中所有
  目录服务连接且工具元数据可用后才允许 worker ready/prompt；失败、超时、取消均返回稳定错误码。
- adapter 的元数据缓存目录绑定当前 Run 的 0700 临时目录，避免 worker 访问宿主 `~/.pi/agent`
  或与其他 Run 发生缓存竞争；正常 dispose 与启动失败均恢复环境并清理临时目录。
- 适配器 readiness 单测覆盖延迟初始化、失败闭门和 stale eager snapshot；生产 Pi session 测试
  证明 readiness 完成前不解析 session、不允许 prompt。
- R2 拓扑 cleanup 使用 shielded task，在 `CancelledError`、`KeyboardInterrupt` 与其他
  `BaseException` 启动失败下仍完成子进程、fake server、数据库种子收口；进程只按本拓扑
  已记录的 PGID 终止，异步轮询替代阻塞式 `proc.wait()`。
- `_InProcessServer.stop` 超时后显式 cancel 并 `gather(return_exceptions=True)`；每个拓扑使用
  唯一 `gateway_id`，破坏性 UAT 清理先硬断言 test 环境、`kol_insight_test` 和 `kol_test`。
- UAT 文件级 fixture 在开始/结束执行安全残留清理，并记录 fake_model/fake_mcp/db/服务 ready、
  cleanup_started、process_reaped 等无密钥生命周期阶段。
- 进程组回收在 SIGKILL 后继续硬等待并 fail-closed；若 PID 未真正 reaped，cleanup 失败，不能
  把残留进程伪装成通过。

### 验证结果

- TDD 红灯：在 readiness 实现前，延迟/失败 session、eager lifecycle 与 readiness gate 测试共 4 项业务断言失败。
- R1 定向 Pi Gateway 测试：13 passed；`npm run typecheck`、`npm run build` 通过。
- 离线进程级首个品牌链路：1 passed；fake MCP 实收 4 次，四次均 settled，钱包净支出 40，报告 Version 与 Evidence 链路通过。
- R2 生命周期单测：5 passed；随机 gateway ID 下首个完整离线品牌链路再次 1 passed。
- 启动失败诊断确认原因为 adapter metadata cache `EPERM`，非业务重试；修复后未出现
  `server_backoff`、`not_connected`、`init_timeout`，也未重放首个业务调用。
- R3 lease 评估：现有 5 秒租约、500ms heartbeat、按剩余租约收紧的 request timeout、两次失败
  上限和 `lease/4` abort grace 已满足 `heartbeat + timeout + failures + grace < deadline`；
  28 个 Gateway lease/heartbeat 测试与 7 个后端 lease/recovery 测试通过，没有合法边界失败，
  因此不修改 `PI_GATEWAY_LEASE_SECONDS`，也不创建空 R3 提交。
- 最终 Pi Gateway 全套门禁曾捕获 1 个未处理 `worker_signaled` rejection；为 isolated worker
  `done` promise 加非侵入式 rejection sink 后，24 个测试文件、127 个测试、typecheck 与 build
  全部通过，显式 await `done` 的业务/崩溃错误语义不变。
- 全量离线 UAT 首次串行运行在第 12 个场景暴露了测试拓扑 PID 探测依赖受限的全局 `ps`；
  该命令在受限执行环境中返回 `EPERM`，并不代表被测 Gateway 进程残留。修复为 Gateway
  仅在 test 环境的 `/metrics` 暴露其自身 active worker PID 集合，UAT 只读取该集合并按
  本拓扑已登记的 PID 发 SIGKILL，删除全局进程扫描依赖；新增 Gateway active PID 生命周期测试。
- 该失败发生在最终三轮 UAT 门禁期间，故三轮 UAT 尚未通过，不能宣告
  `READY_FOR_REAL_B7_UAT_REVIEW`；修复后的全量门禁必须从 Pi Gateway 套件重新开始。
- 追加根因修复：同一事件循环内 `sse-starlette` 的 in-process Uvicorn
  `_shutdown_watcher` 在拓扑结束后残留，导致下一轮 FastAPI 启动卡在
  `insight-cube` `list_tools`；harness 在停止时广播 `AppStatus.should_exit`，有界等待并
  `gather(return_exceptions=True)` 收口 watcher，下一拓扑启动前重置退出标志。另以 Gateway
  test-only `/metrics` 暴露本 Gateway 的 active worker PID，UAT 不再运行全局 `ps`。
- 修正 heartbeat 调度在快速测试/短租约下的 10ms 下限回归为 1ms（仍受配置 interval 与
  lease/3 上界约束），避免初始化期错过首个 lease beat；没有修改租约时长或重放业务调用。
- 首个品牌全链路连续 **10/10** 通过；完整离线进程级 UAT 串行三轮均 **17 passed**，耗时分别
  **279.68s / 279.75s / 280.87s**。后端完整 pytest **2012 passed、22 skipped**，Ruff 通过；
  Pi Gateway **128 passed（24 files）**、typecheck/build 通过；Pi Runtime **47 passed（9 files）**、
  typecheck 通过；前端 **305 passed（40 files）**、lint/build 通过。
- UAT 生成的 6 个 xlsx 已移至 `/private/tmp/b0-gateway-r2-final-20260811/`；测试库检查无
  UAT users/wallets/gateway/nonce，UAT 监听端口与拓扑进程均已收口。其余非 UAT 的历史测试租户
  不在本轮 destructive purge 范围内。
