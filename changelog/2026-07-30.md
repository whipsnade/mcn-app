## 达人详情「热帖服务暂不可用」误报修复（degraded 假失败）

- 现象：抖音达人详情点「刷新」后报「热帖服务暂不可用，已展示达人基础详情」，
  热帖不展示（`posts_degraded=true`）。
- 诊断（SQL 实证）：`quick_mcp_calls` 中详情与热帖两次 MCP 调用均成功，模型
  finish 也拿到了 10 条帖子，但把 `posts_degraded` 标成了 true。即 MCP/上游无问题，
  是模型误判。
- 根因：前一天「热帖链接」修复把 `kol_detail` 的 finish 契约改成「每个帖子对象
  **必须**包含 url（帖子链接）字段」，而抖音上游数据本就没有链接字段（只有
  「内容ID」）。模型理解为「帖子不满足契约 = 获取失败」，于是标 degraded——
  契约硬要求对无 url 的平台造成「假失败」。
- 修复（双保险）：
  1. 契约软要求（`quick/agent.py` 的 `_OUTPUT_CONTRACTS["kol_detail"]`）：去掉
     「必须包含 url」，改为「保留上游原始字段；抖音等平台无直接链接时保留
     「内容ID」即可（代码会自动合成视频链接，不算获取失败）；仅当确实未获取到
     任何帖子时才 posts 空列表 + `posts_degraded: true`」。
  2. 代码护栏（`quick/service.py` 的 `kol_detail`）：`degraded = posts_degraded
     and not posts`，模型误标时以实际数据为准，仅在确实没有帖子时才降级。
- 测试：契约断言同步改为「不算获取失败」语义；新增用例「finish 带 posts 且
  posts_degraded=true 时服务返回 degraded=False」。`tests/quick` 66 passed。
- 前端无需改动（degraded 仅是横幅展示）。

## 会话内多次分析各自保留「执行流程」

- 问题：同一会话多次分析共用一个执行流程（渲染在所有消息之后、只跟踪最新任务），
  新分析一开始旧流程即丢失，无法回看过往执行记录。
- 方案（纯前端，后端零改动）：
  - 新 hook `useTaskFlows`：活跃任务终态后冻结其 runtime；历史任务（用户消息
    metadata 的 `latest_analysis_task_id` 锚点）经 `GET /tasks/{id}/events` 从 0
    回放持久化事件重建流程节点与终态摘要；404 标记 missing 不重试；切会话清空。
  - `ChatArea`：流程卡改为锚定在触发它的用户消息下方——活跃卡保持实时节点 +
    思考块 + 流式草稿，历史卡终态收缩为「执行流程 · 共 N 步 · 分析完成」可展开；
    回放中显示「执行流程加载中…」骨架；底部共享流程区仅在活跃任务尚未锚定的
    窗口期（POST 未返回）显示。
- 测试：useTaskFlows +5（冻结/回放重建/活跃不回放/404 不重试/切会话清空），
  ChatArea +3（双卡锚定与顺序/加载与 missing/活跃卡不重复），全套 1630 passed。

## 三类分析 loop prompt 增加「建议补充信息」要求

- 需求：用户提交品牌/活动/圈选 KOL 问题后，希望模型分析还需要哪些更多信息
  才能更精确地获取结果。

  `AGENT_LOOP_SYSTEM_TEXT`（圈选）、`BRAND_ANALYSIS_LOOP_SYSTEM_TEXT`、
  `CAMPAIGN_ANALYSIS_LOOP_SYSTEM_TEXT`。

## 任务创建前「先澄清一轮」：planner 注入工具清单 + 强制首轮 clarify

- 背景：早先在 loop prompt 里加的「分析还需要哪些信息」不生效——agent loop
  中途没有向用户提问的通道，那句话只能落在 finish 结论里。真正负责提问的是
  任务创建之前的环节；而画像 ready 后消息直接建任务，没有任何追问。
- 目标效果（用户确认）：画像 ready 后每条分析类消息，把「问题 + MCP 工具清单
  + 可执行 goal」交给模型，模型从执行更稳定、数据更精准的角度先追问一轮
  执行条件（一次一问、2-4 个选项），用户回答后再建任务；每个新需求最多一轮，
  用户说「直接执行」可跳过；brainstorm 阶段不动。
- 实现（复用 GoalPlanner enforce 链路，无新端点、前端零改动）：
  1. `goals/context.py`：`GoalPlannerContext` 新增 `available_tools` 字段，
     `build_for_message` 透传（影子入口不注入）。
  2. `tasks/router.py` `_plan_goal_or_fallback`：直接查 `mcp_tool_catalog`
     （is_enabled + review_status=approved）生成紧凑投影
     {internal_name, description, required_params} 注入；拉取失败不阻塞规划。
     注意 `ApprovedTool` 不含描述字段，描述在 catalog 行 `reviewed_description`。
  3. `goals/planner.py`：payload 新增 `available_tools` 键。
  4. `model/prompts.py` `GOAL_PLANNER_SYSTEM_TEXT`（version 1→2）：新增
     「先澄清后执行」规则——分析类意图首轮必须 clarify（围绕 available_tools
     能力问最关键执行条件，选项可转化为工具参数/goal params）；用户已回答或
     说「直接执行」必须 execute 且不得重复追问；respond 三态与操作指令
     （导出 Excel 等）例外不澄清。
  5. 开关：本地与 UAT `.env` 均 `GOAL_PLANNER_ENFORCE_ENABLED=true`（代码默认
     仍 false）。clarify 衔接靠消息历史：澄清问答落 messages 表，用户回答后
     重新走 tasks 端点，planner 经 recent_messages 看到问答即 execute。
- 测试：test_context（tools 透传）、test_planner（payload 含 tools）、
  test_prompt_contract（version=2 + 新规则断言）、test_enforce_create_task
  +2（catalog 注入仅 approved+enabled；clarify→回答→execute 全链路）。
  ruff 通过，pytest 847 passed（1 个真实供应商集成测试因本地 .env 模型
  glm-5.2 与断言 deepseek-v4-pro 不符失败，历史遗留与本次无关）；
  前端 1631 passed + tsc 无错误。
- UAT：rsync 4 个后端文件 + `.env` 开关，重启后 `/docs` 200。
- 遗留：clarify 的 options 不进 planner 后续 prompt（assistant 消息文本含问题，
  可接受）；每条分析消息多一次 planner 往返（零积分，不调 MCP）。
- 后续调整（同日）：澄清轮次由「每个需求最多一轮」改为**模型自主判断**——
  用户回答后模型若仍认为缺关键条件可继续追问（每轮一问），直到它判断执行
  条件足够；约束只有「不得重复追问已回答的条件、通常 1-3 轮收敛、用户说
  直接执行必须 execute」。无服务端硬上限，系用户明确要求的 prompt 级设计。
  prompt 契约断言同步更新，UAT 已同步 prompts.py 并重启。
