# 2026-08-04

## B1：schema 驱动的产物 null 治理 + SentimentBucket 可空（agent-runtime v3 加固 §6.3）

### 背景与目标

审核遗留两问题：五类强类型 payload 的 `SECTION_NUMERIC_PATHS` 手工枚举覆盖严重不全
（数组路径 daily_trend[].*、topics[].*、top_posts[].*、audience[].value/share、
kol_trend[].*、items[].* 等大量遗漏），章节标 complete 但内含 null 数值也能过校验；
`SentimentBucket.count/share` 类型上不可空，治理规则是死代码，情感缺失时唯一合法表达
竟是伪造 0，违反「null 不得当 0」。

### 主要改动

- `backend/app/agent_artifacts/payloads/common.py`：
  - 废除 `SECTION_NUMERIC_PATHS`，改为 `GOVERNED_SECTIONS`（业务章节根 = data 顶层
    字段名）+ `iter_null_numeric_paths`：从 Pydantic 字段注解递归遍历章节下所有
    `int | None` / `float | None` 叶子（含数组元素、dict 值、嵌套模型），发现 null
    时要求该章节 availability 为 partial/unavailable 且有覆盖 limitation（通用 /
    章节级 / 精确叶子路径三级覆盖）。
  - 豁免（§12.1 Lineage 与消费边界）：日期/时间、枚举 Literal、稳定身份与纯文本
    标签（含可空 URL/外键/source/missing_reason）、版本、展示顺序（rank 等不可空
    int 天然豁免）、评分配置（weights/score_snapshot 不可空数值）、运行时元数据
    （kol_detail 的 data.cache：hit/fetched_at/expires_at）。
  - `SentimentBucket.count/share` 改为可空：情感 unavailable 时允许 null +
    limitation；真实零值是数值叶子，发布边界由 lineage `required_numeric_pointers`
    照常要求引用（两者不冲突：null 叶子不产生 lineage 指针）。
- 五个 payload（brand/campaign/kol_selection/kol_analysis/kol_detail）声明
  `GOVERNED_SECTIONS`；kol_detail 豁免 cache；insight_board_v1 无受治理章节。
- builders 稀疏数据适配（不得在校验边界崩溃，必须产出 restricted 合法 Draft）：
  - `builders/kol_selection.py`：items 展示数值（followers/quoted_price 等）出现
    null → items partial + `metric_data_missing` limitation + restricted。
  - `builders/kol_analysis.py`：summary/kol_trend/top_kols 分章节收集 null 叶子，
    任一非空即该章节 partial + limitation + restricted（合并原 null_summary 与
    complete 两分支）。
  - `builders/kol_detail.py`：`_section_plan` 改为按 (code, affected_paths) 多
    limitation 结构，新增 audience 项 value/share null、trend 项 null
    （`trend_partial`）、latest_posts 互动数值 null（`post_metric_missing`）的
    partial 披露。
- 前端最小类型同步：`src/api/agentArtifacts.ts` 新增 `AgentArtifactSentimentBucket`
  （`count/share: number | null`），summary 与 by_platform 复用；组件渲染逻辑不动
  （A7 已把 null 渲染为「数据受限」，tsc 通过）。
- 测试：`tests/agent_artifacts/test_null_governance.py` 新增 30+ 例——五类 payload
  数组内 null 叶子被捕获（daily_trend/topics/top_posts/overview.platforms/
  comparisons.metrics/timeline/kol_contributions/items/quoted_price/kol_trend/
  top_kols/audience/trend/latest_posts 每类至少一例）、章节级与精确路径 limitation
  覆盖、可空非数值豁免、情感 null 三态（complete 拒绝 / partial+limitation 通过 /
  partial 无 limitation 拒绝）、真实零值 lineage 指针存在而 null 不产生、三个
  builder 稀疏数据产出 restricted。

### 验证结果

- `cd backend && .venv/bin/pytest tests/agent_artifacts -q` → **269 passed**（234 + 35 新增）。
- `cd backend && .venv/bin/pytest -q` → **1015 passed / 11 skipped**（基线 962 + 新增，
  零回归；并行任务同 worktree 联调期间其中途编辑造成的抖动已在双方收口后消失）。
- `cd backend && .venv/bin/ruff check app tests` → 通过。
- `npm run test` → 178 passed；`npm run lint`（tsc）→ 通过。

### 遗留事项

- 情感 null 的前端渲染已由 A7 保证；若后续 Evidence 能返回真实 0，发布时需确保
  lineage refs 覆盖对应桶路径（`required_numeric_pointers` 会强制）。
- brand/campaign 无 builder（模型直接产出 payload），null 治理在 Draft 校验边界
  生效，非法产出回喂模型重写而非崩溃（既有行为）。

## B5：kol_detail 名单引用消费 + 前端/端点死代码清理（agent-runtime v3 加固 §6.4）

### 背景与目标

审核遗留三问题：`POST /agent/sessions/{id}/kol-details` 透传的
`selection_artifact_id`/`selection_version` 被 `KolDetailRunService` 静默丢弃（不进
prompt、不进 Artifact parent、不校验归属）；前端一批指向已 404 旧端点的
API/hook/组件死代码；`/favorites/kol-selection-ref` 端点读旧表且前端无调用方。

### 主要改动

- 名单引用消费（`backend/app/agent_runtime/kol_detail.py` 等）：
  - 归属校验 `_resolve_selection_ref`：Artifact 必须属当前 Session 且为
    `kol_selection_v3`，`selection_version` 必须指向其已发布 Version（版本号），
    两字段必须成对；任何失败抛 `KolDetailSelectionRefNotFound`，路由统一 404
    `kol_selection_not_found`（不泄漏存在性，§7）。缓存命中路径同样先校验。
  - 消费链路：解析出的 Version 行 id 写入 `prompt_snapshot_json["kol_detail"]
    .selection_version_id`（G3 恢复锚点同快照）；协调事务把 kol-detail 稳定行
    `parent_artifact_id` 指向名单 Artifact；`CreateDraftTool` 对 module=
    kol-detail 以快照权威覆盖 Draft Revision 的 `parent_artifact_version_id`
    （不信任模型传参，发布时复制进 Version）；触发消息文本携带名单引用
    （`kol_detail_trigger_content` 扩展，transcript 崩溃恢复从同一快照重建）。
- 前端死代码删除（rg + import 图证明无生产引用后删除）：`src/api/tasks.ts`、
  `brainstorm.ts`、`kolSelection.ts`、`sessions.ts`、`platforms.ts`、
  `src/hooks/useWorkspace.ts`、`useTaskStream.ts`、`useTaskFlows.ts`、
  `src/state/taskEvents.ts`、`src/components/BrandReportView.tsx`、
  `TaskFlowNodes.tsx`、`ThinkingPanel.tsx` 及各自测试、`src/test/fixtures.ts`
  （仅 BrandReportView 测试引用）；`ChatArea.tsx` 移除 deprecated 旧任务流
  props 与 type-only 导入；`api/taskStream.ts` 只保留 `parseSseStream`
  （agent.ts 在用）；`api/client.test.ts` 删 tasks 用例；`contracts.ts` 删除
  ApiQuick* 与仅死代码引用的旧契约类型（ApiTask*/ApiSession/ApiMessage/
  ApiThinking*/ApiBrainstormResponse/ApiSelectionSetItem/ApiAnalysisReportSummary/
  CreateSessionInput 等；BrandReport*/ReportBlock/ApiAnalysisReport 等仍被
  types.ts 引用故保留）。
- favorites：`DELETE` 掉 `/favorites/kol-selection-ref` 端点、
  `FavoritesService.resolve_selection_ref`、`serialize_selection_item`、前端
  `getFavoriteKolSelectionRef`/`FavoriteKolSelectionRef` 与相关测试；
  list/create/delete 契约不动。

### 验证结果

- `cd backend && .venv/bin/pytest tests/agent_runtime tests/favorites -q` → 528 passed。
- `cd backend && .venv/bin/pytest -q` → 1015 passed / 11 skipped。

  ApiSessionReportItem/ApiArtifactsSummary 等仅它与 types.ts 引用的类型。

## B2：五类 Artifact Builder 工具（Plan B）

### 背景与目标

修复设计 §3.3/§6.1：真实 UAT 证明模型手写带 lineage 的大型正式 payload 不可行
（45 次决策 17 次 revision 仍不过审）。改为模型提供 scope、Evidence ID 列表
（按章节分组）与叙事字段，Builder 工具读取 Evidence、确定性聚合、生成字段级
lineage、构造并校验强类型 payload 后落 Draft。

### 主要改动（关键文件）

- 新增 `agent_artifacts/builders/brand.py` / `campaign.py`：
  `build_brand_report_draft`（brand_report_v3）与
  `build_campaign_report_draft`（campaign_report_v2）。聚合口径移植自已删除的
  旧 `reporting/brand_assembler.py`（git `d54bc06^`）确定性部分：overview 按
  平台合并声量/互动/发帖、合计行防双计（仅聚合行时归入 all）、mom=紧邻上一
  等长周期/yoy=平移一年（2/29→2/28）、情感计数（声量值缺失按 1）与占比、
  sentiment_score=(正-负)/总量*100；活动无旧确定性真源（旧为模型直出），口径
  对齐品牌：timeline 按 (日期,平台)、platform_contributions share=平台声量/
  总声量、kol_contributions 按 (平台,作者uid) 分组 contribution_share=互动
  占比 Top20、top_posts 互动量降序 Top20。缺失保持 null + partial/unavailable
  + limitation（B1 递归 null 治理），全无证据行抛 DraftBuildError。
- 新增 `agent_artifacts/builders/raw_rows.py`（Evidence 行提取/别名/单位/平台
  归一/情感极性，行级 source_path 供 lineage）与 `sections.py`（brand/campaign
  共用的 sentiment/top_posts 装配）；`builders/common.py` 加 `LineageCollector`
  （字段级引用收集，>12 来源按 Evidence 折叠到最短可解析指针）。
- 新增 `agent_runtime/tools/builders.py`：五个 TrustedTool
  （build_brand/campaign/kol_selection/kol_analysis/kol_detail_report 中的
  build_*_draft），零积分、external_side_effect；Evidence/Artifact 归属校验
  （跨 Session 一律 evidence_not_found 不泄漏存在性），输出只回
  artifact_id/draft_id/revision_id/schema_version + 受限/limitation 摘要，
  不回灌完整 payload。kol_analysis 工具读取父名单已发布 Version 并固定
  parent 绑定；kol_selection 工具委托 rank_kols（落 settled 内部调用供
  derivation）。
- `tools/factory.py`：五个 Builder 注册进 **ARTIFACT_TOOLS** 分类（与
  create/update_draft 同信任层级、同可见 Profile，不另设 BUILDER_TOOLS）；
  kol_detail_v1 按修复设计 §5.1 保留 Builder 能力故可见。

### 验证结果

- `pytest tests/agent_artifacts tests/agent_runtime -q` → 829 passed（新增
  test_brand_builder 17 + test_campaign_builder 8 + tools/test_builders 13，
  含聚合数值断言、restricted 路径、跨 Session/无效 ID 结构化错误、输出不含
  payload、lineage DB freeze 通过）。
- `pytest -q` → 1053 passed / 11 skipped；`ruff check app tests` → 通过。

### 遗留事项

- `CreateDraftTool` 的 kol-detail 快照 parent 权威覆盖逻辑仍只在通用 Draft
  工具上；BuildKolDetailDraftTool 未复制该逻辑（依赖并行任务的 kol_detail
  运行时接线结论），如需统一可在后续任务收口。

  Evidence）；如 Reviewer 要求聚合值必须挂 settled 计算调用，可再引入

## B3：四个 Profile 正式 Prompt + Builder 契约注入核对 + kol-detail Builder parent 一致性（Plan B）

### 背景与目标

修复设计 §6.2：`agent_runtime/prompts.py` 此前只是骨架（自述"完整 prompt 工程
在后续任务完成"），是 UAT 阻断项 2（真实模型 45 决策 17 revision 产不出过审
Artifact）的根因之一。本任务落地四个 Profile 的正式 prompt，核对工具 Schema
上下文注入，注入去敏成功示例，并补齐 B2 遗留：BuildKolDetailDraftTool 缺少
CreateDraftTool 的 kol-detail 快照 parent 权威覆盖逻辑（模型可经 Builder 工具
传错 parent）。

### 主要改动（关键文件）

- `agent_runtime/prompts.py`：四个 prompt 全部重写为正式版，沿用仓库 prompt
  惯例使用中文、分节条款式；版本 v1→v2（prompt 版本随内容修订独立递增，与
  Profile 能力版本解耦，注册表键不变）。session_analyst_v1 覆盖四动作协议、
  澄清时机（一次一问、2-4 选项）、工具准则（MCP 采集 Evidence →
  read_artifact/search_evidence/read_tool_result 游标 → calculation →
  Builder → submit_review）、五类 Artifact 选择指引（brand/campaign/
  kol_selection/kol_analysis 必须走对应 Builder，不手写整份 payload；
  create_draft/update_draft 仅用于 insight_board_v1 与受控修订）、Evidence
  数字纪律、失败处理（换参数/换工具/继续其他维度、unknown 绝不重放、余额
  不足基于已有证据受限交付）、restricted 诚实披露；显式声明不规定固定业务
  阶段或固定工具顺序（设计红线，测试双向断言守住）。artifact_reviewer_v1
  覆盖五项审核清单、approve/revise/reject 语义与 restricted 放行条件。
  kol_detail_v1 覆盖缓存优先（服务端先行，进入 Run 即缓存未命中）、MCP
  allowlist（kol_detail/query_raw_posts）+ Builder、最多 5 条热帖、URL 缺失
  披露不伪造、无 ask_user。utility_v1 覆盖 session_title/run_summary/
  suggestions 输出契约。
- 上下文注入核对结论：`memory.py` 的 MemoryContextBuilder 每轮已注入
  available_tools（含 input_schema、points_cost、description）与 wallet
  余额，Builder 输入契约（Evidence 分组/叙事字段）B2 已写进工具描述——无需
  补代码，新增契约测试锁定（test_context_injects_builder_tool_input_schemas）。
- 成功示例：`model/exemplars.py` 与 model_prompt_logs 在当前架构下可用
  （网关 complete_json 统一落 prompt 日志，purpose=agent_loop），按旧模式在
  MemoryContextBuilder 注入 "exemplars" 键（同用户最近成功记录 ≤2 条，
  _prune_sensitive 剔除 key/token 字段、截断 ~1500 字符；检索异常 best-effort
  降级空列表不阻塞主流程）。
- `tools/artifacts.py`：CreateDraftTool 的 kol-detail 快照 parent 逻辑提取为
  模块级 `kol_detail_snapshot_selection_parent`；`tools/builders.py` 的
  BuildKolDetailDraftTool 复用该函数，Run 快照携带 selection_version_id 时以
  快照权威覆盖 parent_artifact_id/parent_artifact_version_id（dataclasses
  .replace，不信任模型传参），两条 Draft 路径语义一致。

### 验证结果

- TDD：先写失败测试（16 个红），实现后全绿。
- `pytest tests/agent_runtime tests/agent_artifacts -q` → 846 passed（新增
  test_prompts 11 + test_memory 4 + test_builders 2）。
- `pytest -q` → 1070 passed / 11 skipped；`ruff check app tests` → 通过。

### 遗留事项

- Builder 路径的 parent 覆盖只纠正 Draft 绑定字段；模型传错的
  selection_artifact_id/selection_version 仍会进入 payload scope（与
  CreateDraftTool 等价——payload 属模型内容，绑定属服务端权威）。如需连
  scope 一并纠正，可另立小任务。
