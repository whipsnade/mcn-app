## B1：schema 驱动的产物 null 治理 + SentimentBucket 可空（agent-runtime v3 加固 §6.3）

### 背景与目标

审核遗留两问题：五类强类型 payload 的 `SECTION_NUMERIC_PATHS` 手工枚举覆盖严重不全
（数组路径 daily_trend[].*、topics[].*、top_posts[].*、audience[].value/share、
kol_trend[].*、items[].* 等大量遗漏），章节标 complete 但内含 null 数值也能过校验；
`SentimentBucket.count/share` 类型上不可空，治理规则是死代码，情感缺失时唯一合法表达
竟是伪造 0，违反「null 不得当 0」。

### 主要改动

- `backend/app/agent_artifacts/payloads/common.py`：
  - 废除 `SECTION_NUMERIC_PATHS`，改为 `GOVERNED_SECTIONS`（业务章节根 = data 顶层
    字段名）+ `iter_null_numeric_paths`：从 Pydantic 字段注解递归遍历章节下所有
    `int | None` / `float | None` 叶子（含数组元素、dict 值、嵌套模型），发现 null
    时要求该章节 availability 为 partial/unavailable 且有覆盖 limitation（通用 /
    章节级 / 精确叶子路径三级覆盖）。
  - 豁免（§12.1 Lineage 与消费边界）：日期/时间、枚举 Literal、稳定身份与纯文本
    标签（含可空 URL/外键/source/missing_reason）、版本、展示顺序（rank 等不可空
    int 天然豁免）、评分配置（weights/score_snapshot 不可空数值）、运行时元数据
    （kol_detail 的 data.cache：hit/fetched_at/expires_at）。
  - `SentimentBucket.count/share` 改为可空：情感 unavailable 时允许 null +
    limitation；真实零值是数值叶子，发布边界由 lineage `required_numeric_pointers`
    照常要求引用（两者不冲突：null 叶子不产生 lineage 指针）。
- 五个 payload（brand/campaign/kol_selection/kol_analysis/kol_detail）声明
  `GOVERNED_SECTIONS`；kol_detail 豁免 cache；insight_board_v1 无受治理章节。
- builders 稀疏数据适配（不得在校验边界崩溃，必须产出 restricted 合法 Draft）：
  - `builders/kol_selection.py`：items 展示数值（followers/quoted_price 等）出现
    null → items partial + `metric_data_missing` limitation + restricted。
  - `builders/kol_analysis.py`：summary/kol_trend/top_kols 分章节收集 null 叶子，
    任一非空即该章节 partial + limitation + restricted（合并原 null_summary 与
    complete 两分支）。
  - `builders/kol_detail.py`：`_section_plan` 改为按 (code, affected_paths) 多
    limitation 结构，新增 audience 项 value/share null、trend 项 null
    （`trend_partial`）、latest_posts 互动数值 null（`post_metric_missing`）的
    partial 披露。
- 前端最小类型同步：`src/api/agentArtifacts.ts` 新增 `AgentArtifactSentimentBucket`
  （`count/share: number | null`），summary 与 by_platform 复用；组件渲染逻辑不动
  （A7 已把 null 渲染为「数据受限」，tsc 通过）。
- 测试：`tests/agent_artifacts/test_null_governance.py` 新增 30+ 例——五类 payload
  数组内 null 叶子被捕获（daily_trend/topics/top_posts/overview.platforms/
  comparisons.metrics/timeline/kol_contributions/items/quoted_price/kol_trend/
  top_kols/audience/trend/latest_posts 每类至少一例）、章节级与精确路径 limitation
  覆盖、可空非数值豁免、情感 null 三态（complete 拒绝 / partial+limitation 通过 /
  partial 无 limitation 拒绝）、真实零值 lineage 指针存在而 null 不产生、三个
  builder 稀疏数据产出 restricted。

### 验证结果

- `cd backend && .venv/bin/pytest tests/agent_artifacts -q` → **269 passed**（234 + 35 新增）。
- `cd backend && .venv/bin/pytest -q` → **1015 passed / 11 skipped**（基线 962 + 新增，
  零回归；并行任务同 worktree 联调期间其中途编辑造成的抖动已在双方收口后消失）。
- `cd backend && .venv/bin/ruff check app tests` → 通过。
- `npm run test` → 178 passed；`npm run lint`（tsc）→ 通过。

### 遗留事项

- 情感 null 的前端渲染已由 A7 保证；若后续 Evidence 能返回真实 0，发布时需确保
  lineage refs 覆盖对应桶路径（`required_numeric_pointers` 会强制）。
- brand/campaign 无 builder（模型直接产出 payload），null 治理在 Draft 校验边界
  生效，非法产出回喂模型重写而非崩溃（既有行为）。

## B8：MCP 调用墙钟超时按 result_unknown 收口（cutover 阻断项 1 / UAT Incident #8）

### 背景与目标

真实 UAT（`docs/qa/2026-08-02-agent-runtime-uat.md`）场景 2/3/4 挂死的根因：DataTap
某些统计查询长时间持续 trickle 返回数据，`transport.call_tool` 挂起数十分钟。挂起层在
MCP SDK `streamable_http_client` + `ClientSession.call_tool` 的流式等待：httpx
`read_timeout`（60s）是"无活动"超时，trickle 数据持续到达时被不断重置而永不触发；
per-service 队列等待有独立 300s `wait_for`、连接有 5s connect timeout，都不是挂点。
UAT 记录"`asyncio.wait_for` 无法打断 httpx C 层阻塞"——httpx 实为纯 Python（anyio 后端），
无 C 层阻塞，取消通常可传播；但实现不依赖该假设：墙钟收口必须即使底层吞掉取消也按时生效。

### 主要改动

- `backend/app/mcp_gateway/datatap.py`：`DataTapTransport` 新增
  `call_timeout_seconds`（默认 None 不启用，legacy 行为不变）与 `cancel_grace_seconds`
  （默认 5s）。`_run_isolated` 的外发阶段改经 `_dispatch_with_wall_clock`：拿到
  per-service 队列许可后开始计时（队列等待不耗预算）；超时先取消底层任务并在宽限内
  等待其真正退出——**不用 `asyncio.wait_for`**（它超时后会无限期等待被取消任务退出，
  底层不可取消时依旧挂死）；宽限过后仍不死则隔离悬挂任务（`_track_abandoned`：保留
  引用防 GC、done callback 吞噬异常并记 warning），随后抛 `PossiblySentTimeout`。
  外层被取消（引擎停机）时同样取消并隔离内层任务。已确认结果的 `_recent_results`
  缓存、故障分类映射、队列/熔断语义均不变。
- `backend/app/core/config.py`：新增 `AGENT_MCP_CALL_TIMEOUT_SECONDS`（默认 150.0s，
  须小于 `AGENT_TOOL_CALL_STUCK_SECONDS`=900s）。
- `backend/app/mcp_gateway/service.py`：仅 Agent 传输（`get_agent_mcp_transport`）
  注入墙钟；超时经既有 `PossiblySentTimeout → _UNCONFIRMED_ERRORS` 分类落
  `result_unknown`——保留 10 积分预留、`agent_tool_calls.status="unknown"`、计细粒度
  熔断失败（同参数反复超时会被熔断）、Run 继续后续工具；恢复循环 stuck 扫描与 unknown
  只读核对对该类行照常生效，确认后 settle/release 幂等、绝不重复扣费或重放。
- 测试（TDD 先红后绿）：`tests/mcp_gateway/test_call_timeout.py` 7 个（挂起 trickle
  按时收口 / 吞取消顽固层按时收口+悬挂隔离 / 快调用不受影响 / 队列等待不计入预算且
  超时后同服务下一调用可继续 / 非超时故障分类保持 / 缺省不启用 / 非法配置拒绝）；
  `tests/agent_runtime/tools/test_mcp.py` §8 3 个（真实传输挂起 → unknown 收口+预留
  保留 / 超时计熔断失败 / unknown 核对只读不重放 + confirm_success/confirm_failure
  结算释放幂等不重复扣费）；`test_runtime_wiring.py` 1 个（Agent 传输启用墙钟、
  legacy 不启用）。
- `docs/runbooks/agent-runtime-v3-cutover.md`：阻断项 1 状态更新为"已修复（运行时墙钟
  收口），待真实 UAT 复核"，写明机制、配置项与调查结论。

- `pytest -q` → 1081 passed / 11 skipped（HEAD 为 1070，新增 11 个用例）。
