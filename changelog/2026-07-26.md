# 2026-07-26

## 模型思考流：MiniMax `<think>` 兼容、会话 SSE 与可恢复展示

### 背景与根因

- 本地真实供应商切到 MiniMax-M3 后，Brainstorm 曾返回
  `MODEL_PLAN_INVALID`，接口随之报 502。根因不是 JSON 内容不合法，而是
  OpenAI 兼容响应正文会在合法 JSON 前附带 `<think>...</think>`；旧适配器把
  整段正文直接交给 Pydantic 做 JSON 校验，因前缀不是 JSON 而判定失败。
- 同一类思考内容还可能来自流式 delta 的 `reasoning_content` 字段。若只兼容
  正文标签，会漏掉供应商原生 reasoning；若直接把整段正文展示，又会把 JSON
  结果混进思考区，并可能暴露系统提示、Schema 或凭证。
- 本次目标是在不改变模型业务结论、任务状态机、报告与计费语义的前提下：
  结构化输出只校验 JSON，思考内容经安全处理后按会话实时展示，并在终态附着到
  assistant 消息供刷新恢复。

### 模型适配策略

1. `backend/app/model/structured_output.py` 提供统一解析器：
   - 非流式响应从正文提取唯一、配平的 JSON 对象，兼容 JSON fence 和
     `<think>` 前缀；缺失、截断或出现多个对象仍按无效结构化输出处理。
   - 流式响应同时消费 `reasoning_content` 与正文中的 `<think>...</think>`，
     思考 delta 与 JSON 正文分离；只把提取后的 JSON 交给输出模型校验。
   - prompt 学习日志继续记录供应商原始响应，便于排障；用户可见思考只走脱敏
     后的 Sink，两者职责不混用。
2. 带 Thinking Sink 的结构化调用优先请求流式响应；只有供应商明确声明
   `stream` 参数不支持时才降级为非流式，再一次性分离 `<think>`。普通 400、
   模型不支持、响应格式不支持和已产生可见输出后的断流不伪装成降级成功。
3. JSON 修复重试按 attempt 分块：首轮无效会结束为 interrupted，第二轮使用新
   attempt，前端标记“正在修正输出格式”；第二轮仍无效才返回
   `MODEL_PLAN_INVALID`。

### Session SSE、turn 与持久化契约

- 前端每次提交生成 UUID `turn_id`，Brainstorm 与任务创建请求都携带该值。
  后端把它写入用户消息 `metadata.turn_id`；任务 retry 复用原 trigger message，
  因而继续归属原 turn。
- 会话级流为 `GET /api/v1/sessions/{session_id}/events`。订阅前校验当前用户对
  会话的所有权，跨用户或跨会话不可订阅。事件类型为：
  `thinking.started`、`thinking.delta`、`thinking.snapshot`、
  `thinking.completed`、`thinking.failed`。
- 事件载荷的稳定字段为 `operation_id`、`turn_id`、`session_id`、`purpose`、
  `attempt`、单调递增的 `sequence` 与 `label`；按上下文可附带 `task_id`、
  `goal_id`、`trigger_message_id`、`text`、`status`、`duration_ms`、
  `error_code`、`truncated`。前端按 session、operation+attempt 与 sequence
  去重，delta 追加、snapshot 替换。
- 终态 block 以 `metadata.thinking = {version: 1, status, blocks}` 附着到同 turn
  的 assistant 消息；成功为 completed，模型或任务失败为 interrupted。assistant
  尚未创建时可以内部暂存到用户消息 `thinking_pending`，但 workspace serializer
  白名单不会把 `thinking_pending` 返回 API，挂接完成后该内部字段被清理。
- 运行中默认展开；operation 完成或失败后自动折叠。刷新后从
  `metadata.thinking` 恢复，仍可手动展开查看；实时 block 与历史 block 按
  operation+attempt 合并，不重复展示。

### 用户可见 purpose 白名单

只给能与当前用户 turn 建立明确归属的调用创建 Sink：

- `brainstorm`：`正在理解需求`
- enforce 模式 `goal_planner`：`正在规划分析目标`
- `agent_loop`：`正在分析数据`
- 任务内自动 `kol_analysis`：`正在生成KOL报告`
- 任务内 `brand_analysis`：`正在生成品牌报告`
- 任务内 `campaign_analysis`：`正在生成活动报告`

以下后台或同步调用不创建用户可见 thinking operation，继续走非流式结构化请求：

- GoalPlanner shadow、`goal_summary`、followup suggestions
- quick 系列调用与活动评估
- 手动 KOL 分析、手动品牌/活动报告重试
- 没有合法 turn/user/session 归属的 legacy 或后台调用

### 安全、限长、断线与失败隔离

- 展示前统一隐藏 Bearer、JWT、API key/token/secret、`sk-` 形式密钥、系统提示词
  片段和 JSON Schema；原始敏感文本不进入 SSE 或消息 metadata。
- 单 operation 最多展示 12,000 字符，同一 turn 最多 30,000 字符；超限追加
  “思考内容过长，已截断”并设置 `truncated=true`。错误码另限 200 字符。
- 每个订阅队列上限 32；消费者落后时清空旧队列并发送当前 operation snapshot，
  避免 delta 缺口继续累积。前端断线后以 25ms 起、最高 1s 的指数退避重连；
  新订阅会收到仍在运行 operation 的 snapshot。切换会话或卸载时 abort 并清理
  监听器，旧会话事件不能写入新会话。
- Thinking Sink 的 started/delta/completed/failed、SSE publish、block 读取与
  持久化都在边界吞掉自身异常并记录 warning；Sink、SSE 或 thinking 持久化故障
  不改变 Brainstorm/GoalPlanner/Agent Loop 决策，不阻断三类任务内报告，也不
  影响 MCP 预留、结算或失败释放。

### 尚存限制

- `SessionThinkingService` 的运行中 operation、订阅队列和未完成 delta 仅保存在
  当前后端进程内。若后端在 operation 未完成时重启，这部分尚未持久化的 delta
  无法恢复；已形成终态并写入 assistant `metadata.thinking` 的 block 不受影响。
- SSE 重连只对当前进程内仍在运行的 operation 生成 snapshot，不提供历史终态
  event replay；历史展示以消息 metadata 为准。
