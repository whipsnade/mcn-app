# Marketing MCP Gateway 未来方案（方案 C）

> 状态：已记录，暂缓实施
>
> 日期：2026-08-07
>
> 启动条件：Pi RPC POC、生产 Pi Agent Gateway、三类报告和真实多租户 UAT 均稳定后，
> 由 Codex 主动提醒用户评估；只有用户再次明确批准后才能进入详细设计与实施。

## 1. 记录原因

当前选择让 Pi 直接连接 DataTap MCP，以最少中间层验证通用 Agent 的真实研究效果。这条
链路适合 POC 和早期灰度，但生产规模扩大后会面临凭证下发、租户隔离、原子计费、调用
审计、供应商切换、限流和幂等边界分散的问题。

方案 C 在 Pi 与 DataTap 之间增加项目自有的 Marketing MCP Gateway，但不能退化为旧式
代码编排器。它只提供协议、治理和观测能力，不决定业务意图、工具顺序或补查策略。

## 2. 允许承担的职责

- 以租户身份代理 MCP 连接，不向 Pi 子进程暴露长期供应商密钥。
- 对调用执行 License、配额、积分预留/结算、限流和审计。
- 生成稳定 call id、Evidence id、原始 payload hash 和 lineage。
- 统一供应商网络超时、连接池、熔断可观测性和 `unknown` 状态，但错误仍原样返回 Pi。
- 支持 DataTap 地址/版本迁移及未来多供应商工具目录映射。
- 对 Schema digest 变化进行隔离和管理员审批。

## 3. 明确禁止

- 不根据“品牌/活动/达人”选择工具。
- 不自动拆分时间窗、补参数、改写查询、吞掉错误或伪造空结果。
- 不对模型隐藏 DataTap 的业务字段或错误语义。
- 不把固定工作流重新塞回网关。
- 不绕过 FastAPI 的 Artifact Builder 与不可变发布门禁。

## 4. 与当前方案的兼容边界

Pi 侧应依赖稳定的 MCP 工具契约和 `_runtime_metadata`，不依赖直连实现细节。未来切到方案 C
时，Skills、Artifact Builder、BI、Excel 和会话交互不应变化；只替换 DataTap 连接配置与
透明审计/计费实现。
